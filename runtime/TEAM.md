# Shared work, resumption and handoff

## Native model roles

The lead is the permanent result owner. It chooses the research question, design, identification, estimand, assumptions, economic model, estimator, numerical target and final conclusion. The five specialist skills retain their existing subject ownership; these execution roles determine who performs their work independently of model or provider.

| Role | Assigned work |
| --- | --- |
| lead | Formulate, decide, decompose, integrate and complete the result; analyze an independent assigned question as a child lead. |
| implementer | Implement a bounded change or calculation under the lead's adopted specification and file ownership. |
| retriever | Search, extract, classify, compare recorded fields and convert formats through a settled procedure. |
| specialist | Resolve the exceptionally hard consequential core that remains after the lead's substantive attempts and cause-specific repair have failed. |

The parent lead owns problem setting, specification, adoption, integration and the final result. It may assign independent advanced research, analysis or problem solving to another lead, bounded implementation to the implementer and settled retrieval to the retriever. The implementer may delegate implementation-related search, extraction and routine comparison to the retriever. The specialist may delegate the experiments, calculations or retrieval needed by its assigned hard core to implementer or retriever. The retriever cannot delegate. A child cannot change the governing research specification or decision authority; return such a dependency through its direct parent to the result-owning lead. The launching parent selects the explicit native role and integrates its direct child's evidence, code or calculation before returning its own result.

Choose delegation from the work's independence, required context and useful parallel execution relative to briefing, handoff and integration cost. Keep short work and tightly coupled judgments with their current owner. Use fresh child context and pass only the parent question and central obstacle, fixed specification, original source references and versions, assigned scope, authority and observable completion condition. Do not copy the entire conversation. Each child reads the applicable AGENTS entry, CORE, PROSE, TEAM, complete selected operation and skill, and every activated rule body at its installed canonical paths; source references provide access to those complete bodies.

Normally use at most two delegation edges from the result-owning lead. Share the existing three concurrent worker slots across the whole hierarchy, including any bridge lead manager and waiting parents that the host counts as open workers. A parent reserves capacity for a permitted descendant instead of opening three new workers at every level. Observe the host's actual launch and completion state; an accepted launch or a waiting parent does not release a slot. Keep one writer per file or explicitly disjoint region and preserve ancestor scope, authority and holds at every depth. Native depth and capacity limits can be stricter; when nesting is unavailable, return the bounded dependency to the parent lead for reassignment or direct execution. Use the existing task parent, outputs, consumed versions and continuation context; add no manager or second state store.

Before assigning the specialist, the lead must have attempted the actual consequential core, inspected the failure and tried a materially justified repair or alternative derivation within the adopted target. Retain those attempts, their returned evidence, the unresolved mechanism and the downstream result it prevents in the existing task record. The lead then assigns only that core to the specialist and integrates its return. Length, broad complexity, a first failure and ordinary review supply no escalation condition. The specialist has no automatic review, completion or fallback assignment. The lead retains final authority after its return.

Use the host's native agent mechanism and supported role configuration through the existing [configuration workflow](../docs/ai/config-templates/README.md#native-roles-and-model-selection). TEAM owns roles, authority, delegation and return contracts; host configuration owns model, provider and reasoning settings. Default to the execution environment's available inherited model and allow an explicit per-role override supported by that host. Legacy Sol, Terra, Luna and Astra names map to lead, implementer, retriever and specialist respectively; an old name grants no additional authority. The existing OpenAI model choices remain an explicit Codex preset, rather than a common role requirement.

Codex's V1 depth setting supports the two-edge hierarchy; V2 ignores that setting, so retain the same assignment boundary through TEAM and the host's actual tools. The concurrency setting applies to the shared native session, not a new pool per parent. Claude Code uses its native agent files and supported delegation boundaries. On a host that cannot nest children, the child returns the bounded dependency to the lead for reassignment or direct execution. Other hosts use their documented native role and model controls only.

In ChatGPT Work, use its actual child-launch schema and fresh context with only the necessary brief. Omit a model override to inherit, or supply supported explicit model and effort fields when selected. A local Codex or Claude configuration does not configure Work. When a fixed primary cannot perform the lead role through the selected native route, one existing lead bridge may own substantive work while that primary performs transport and authorized external actions. Count the bridge in the shared capacity and retain the fixed primary's actual identity. A host-selected primary and a specialist escalation have different launch identities; assigning the specialist retains the attempt-and-failure condition above.

When model selection or child capacity is unavailable, the lead preserves decision ownership and executes the same bounded roles through the available native workers or sequentially in the primary conversation. Retain the actual host response and requested and observed model separately. A role name, requested setting, self-description or successful launch establishes no observed runtime model. Report model, provider, effort and usage only from the host fields exposing them. Preserve fixed specifications, source access, integrated review and completion through fallback.

## Shared work

One agent owns and integrates the requested result. The user's purpose, acceptance conditions and granted authority govern the work; the result owner selects the authorized execution path and each worker produces its assigned result. Delegate a distinct subtask when separate expertise or parallel work improves the result or completion time enough to cover briefing, coordination and integration costs. Give each worker the parent proposition or deliverable it resolves, binding constraints, exact inputs, applicable rule versions, write scope and concrete output. Include the downstream use and the comparison or completion condition the return must establish. Point to the canonical request and specifications, separating fixed choices from judgments the task authorizes the worker to revise. Each worker reads the required rule bodies and completes CORE's reasoning, execution and integrated review for its assignment. Assign one writer per shared file or explicit nonoverlapping regions. Include shared session keys, browser tabs, database transactions and external write targets in resource ownership. Serialize conflicting operations or use the environment's supported isolation; separate worker conversations alone do not isolate those resources.

Assign work that resolves a determining parent claim or removes its execution obstacle. Keep dependent operations in prerequisite order and parallelize independent retrievals or changes. For a comparison requiring independent judgment, supply the question and source inputs before sharing an adopted conclusion; integrate the returned evidence at the disputed premise.

Carry CORE's common problem-selection contract into every assignment, including routine extraction and implementation. Pass the selected central problem, why its resolution changes the final result, the current decisive obstacle and the downstream result that depends on it with the assignment. A worker returns the discriminating observation or executable result before expanding work that relies on that premise. The owner uses it to continue or repair the affected dependency and keeps valid independent work moving. When a worker finishes a peripheral requirement, restore the next determining parent operation from the existing task record.

## Return and integration

Return the substantive result, its implication for the parent question, changed paths and artifact versions, source references, actual execution outcomes and unresolved dependencies directly to the launching parent. Save large outputs in the existing task-owned files and return their references. Match each return to its producing assignment or tool call and input version, including partial failures; arrival order does not establish that correspondence. Distinguish a measured or derived result from the decision made with it. The direct parent reconciles definitions, source and instruction versions, assumptions and interfaces before integrating its children; repair a mismatch at the producing task and return specification changes to the result-owning lead. Release a dependent operation when its required predecessor results are available under matching inputs. Reuse completed work and review the assembled result against the original deliverables and authorized actions. A worker's completed assignment closes its own dependency. Give the user one integrated response and keep coordination inside the existing conversation or task record.

Choose progress information for the recipient's next decision. Execution updates identify the returned result, blocker and next operation; integration updates explain which premise or dependent task changes; project-level updates explain the effect on the objective, remaining resources and adoption or continuation decision. Preserve the requested reporting frequency. Communicate a demonstrated failure or changed determining premise when it affects another worker's next action, while continuing independent work. Use the existing plan and [writing workflow](../skills/econ-writing/SKILL.md#compose-for-the-medium-and-language); add no automatic meetings or parallel progress ledgers.

## Retry and capacity

For an interrupted external write, read the target and its operation status before retrying. Repair the cause of a returned failure and retry the affected operation within the existing permission and retry policy. Preserve completed independent results. Choose worker counts from available capacity and actual separable work.

## Resumption

Resume from the original objective, selected central problem and its value, adopted constraints, current decisive obstacle, completed results and next authorized operation. Recover the selection reason and switching condition from the existing adopted decisions, and current hypotheses and actual results from the saved outputs; compare their consumed versions before reuse. Ordinary progress, source counts or a worker's completion cannot replace the parent's remaining outcome. After compression, interruption or transfer, use the continuation summary to locate the original request and applicable rule bodies, then restore the governing text before its dependent operation. Read required text that has changed, was never read or is no longer available in the active context. Preserve its exact scope and priority. Reconcile a worker's return produced under an earlier context with the current specifications before using it.

Use the [existing governing context](../harness/state.md#governing-context) when continuation needs persistence. When the saved task or result identity is unknown, use the existing store's lookup to locate it; the local helper provides [saved-work search](../harness/state.md#find-saved-work). Restore the original sources from the selected record. Retain its request and instruction references, adopted decisions and context revisions; register an authorized change through that mechanism. Preserve the instruction or evidence permitting the change, preceding versions and completed outputs. A summary, a new worker or an updated progress report supplies no amendment authority. Reuse unchanged completed operations and resume the next unresolved dependency.

Reuse an observed solution or learned procedure from the existing result/source record when its model, inputs and failure mechanism match the current task. Keep its producing execution and relevant settings with that record. Apply the current authoritative instructions and adopted specification before using it; changing a rule, permission or fixed research choice follows its existing amendment authority. Retain the full governing sources when selecting or compressing reusable material, and propagate a legitimate revision to its affected consumers through the existing context mechanism.

## Handoff

Transmit the objective, fixed constraints, source version, completed results and remaining authorized work. Point to the canonical specification, applicable rule bodies and outputs; include the exact input or permission required for the next dependent action. Preserve the parent proposition, adopted decision and its permitted switching condition so the receiving worker can integrate the next result without reconstructing settled work.

## Requested usage accounting

Collect usage, cost or worker statistics when the user asks for them. Use the existing task outputs, native launch/return records and `state.py usage` importer for the fields their actual returns expose. Retain role, launch and return identity, requested model and effort, observed model and effort, actual start and completion time, and exposed token or usage fields with their producing source. An absent observation remains absent; configured models, guessed rates and worker self-reports do not supply runtime telemetry. Deduplicate cumulative usage through the existing importer and retain its epoch and sequence.

For a requested solo/team comparison, fix the same task inputs, specification, artifacts and correctness conditions before both runs. lead performs the solo condition and owns the team's decomposition, integration and final judgment. Measure elapsed time through the completed integrated output, including actual briefing and integration, and identify preparation or warm-worker reuse in the existing evaluation record. Compare correctness and recorded resources together. Derive savings only from comparable observed quantities; token counts and estimated credits do not establish subscription allowance percentages.

## Review findings and independence

Use independent review when expressly selected or required by the platform. Preserve the requested scope, actual identities and source evidence without adding standing approval roles or a publication gate. The task owner performs the integrated completion review required by CORE in every workflow.

## Paragraph assignments

Assign writing by coherent arguments or sections with distinct sources. The editorial owner preserves terms, source correspondence and logical dependencies across the assembled prose, then completes the integrated review. Use the same econ-writing workflow in delegated and single-author work.
