# Shared work, resumption and handoff

## Native model roles

The lead owns the question, adopted specification, decisions, integration and completion. Specialists retain subject ownership. Execution roles are independent of model/provider: `lead` resolves and integrates; `implementer` handles bounded changes or calculations; `retriever` performs settled retrieval or conversion; `specialist` resolves a consequential hard core after substantive lead attempts and cause-specific repair.

Inherit the host model by default. Use a supported override only when its capability, cost or completion time improves the assignment; host launch fields establish actual model and effort. Role labels and requested settings do not prove runtime identity. Local Codex/Claude settings do not configure ChatGPT Work; legacy role presets remain in [configuration](../docs/ai/config-templates/README.md#native-roles-and-model-selection).

Normally allow two delegation edges within the host's shared capacity, reserving room for a necessary descendant. Retrievers cannot delegate. Without nesting or capacity, return the dependency for sequential work. Each child reads its original applicable instructions under CORE; a parent summary cannot replace them.

## Shared work

Delegate separable work only when its benefit exceeds briefing and integration. Each assignment identifies the parent result, obstacle, exact source/rule versions, fixed specification, delegated choices, write scope, output, consumer and completion condition. Assign one writer per file or disjoint region; coordinate shared sessions and external targets. A child cannot amend the governing request or authority.

## Return and integration

Return the substantive result, implication, changed paths, producing inputs/versions, evidence, actual operation returns and remaining dependency to the direct parent. Keep large artifacts in owned paths. The parent matches the return to its assignment, reconciles scientific definitions and interfaces, repairs mismatches at the producer and completes the original deliverable. Give one integrated user response; use existing context for coordination.

## Retry and capacity

Before retrying an interrupted external write, inspect that target's actual status. Repair the returned cause, retry the affected action and preserve completed independent work. Select worker count from actual capacity and separable work.

## Resumption

Restore the original request, central problem, fixed specification, authority, completed results and next authorized action. Recover original applicable rule bodies under [CORE](CORE.md#task-entry), and reuse outputs only with matching consumed versions. Reconcile older worker returns before integration. Use the existing [governing context](../harness/state.md#governing-context) and [saved-work lookup](../harness/state.md#find-saved-work) when persistence is needed.

## Handoff

Pass that same recovery context with canonical source/output locations, the parent proposition, adopted decision, permitted switching condition and essential user-held input for the next action.

## Requested usage accounting

Collect usage only when requested, from actual host fields and existing outputs. `state.py usage` deduplicates cumulative observations. Retain source-backed role, requested/observed model and effort, times and exposed token/usage values; never invent telemetry, prices or subscription percentages. A solo/team comparison uses equal inputs, specification and completion criteria, including briefing/integration costs.

## Review findings and independence

Independent review requires an explicit request or platform instruction. Preserve its scope and evidence; add no standing approval role. CORE's integrated review remains with the task owner.

## Paragraph assignments

Assign coherent arguments with distinct sources. The editorial owner integrates terminology, evidence and logical dependencies through econ-writing.
