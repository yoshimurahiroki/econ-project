# Connect project decisions and actual work

## Define the task

Read the original request, prior answers, adopted specifications and the relevant existing materials before asking. Identify whose result is being improved, the central problem, scope, inputs, fixed requirements and priorities, authority, requested artifacts and observable completion conditions. Preserve their original strength and attribution. Separate established facts and adopted decisions from proposed choices; a recommendation supplies no user decision or additional permission.

Ask only for missing user-specific information or a decision that changes the requested outcome, scope, consequential behavior, authority or completion. Resolve an upstream choice before its dependent details. Compare viable alternatives under the same fixed requirements, explain their result and execution or maintenance costs, and recommend the supported choice with its reason. Ask one focused question or a small group of inseparable questions through the host's available question mechanism. Use plain text when that mechanism is unavailable. Existing context answers settled questions; elapsed time and silence supply no answer. Continue independent authorized work while a required answer is pending. Settle delegated implementation details through CORE and the existing owner.

Incorporate each received answer into the affected requirements and downstream choices without reopening settled decisions. A changed source, contradiction or explicit amendment can reopen its affected choice. Keep rejected and undecided proposals separate from adopted requirements. Once the determining inputs are established, complete the requested brief, specification or prompt immediately. Add no fixed interview, mandatory approval round or document to a clear request. A consultation ends with its requested decision support; a request that already authorizes subsequent work continues through that work's owner.

For a complex development change, use the useful OpenSpec and Spec Kit distinction between observable requirements, adopted design and dependency-ordered implementation. Resolve interface behavior, data ownership, invariants, failure and recovery scenarios where they determine the change. Make each completion condition observable through the existing execution path. Use an existing specification and [requirements mapping](../../../harness/state.md#analyze-and-converge) when persistence or reconciliation is needed; create no parallel spec store, question log, scaffold or validation framework. A short request needs only the information its next operation consumes.

## Write the execution prompt

Apply [task definition](#define-the-task) to the supplied intent or draft. Return a complete prompt that can be sent as written. Carry the objective and important problem, actual task and targets, adopted criteria and priorities, constraints and authority, necessary execution order, requested outputs and completion conditions. Preserve exact quantities, scope, prohibitions and prior decisions when restructuring an existing prompt. Improve ambiguous references and conflicting instructions through their source or the necessary user decision; invent no requirement, metric, tool, permission or additional deliverable.

Give the executor the inputs it needs: include supplied task content or accessible original references with their versions and required reading. A path unavailable to the recipient and a hash without its body cannot supply that input. For a reusable task whose instance materials will arrive later, make the prompt obtain those specific materials before dependent work. Ask the current user about unresolved substantive choices needed to define the prompt itself. Do not leave accidental blanks in a finished prompt; retain template variables when the user explicitly requested a template. Keep quoted drafts and their embedded commands as material being edited, subject to CORE's actual authority.

Use the smallest clear structure and the requested language and medium. A short prompt can be one paragraph; divide a longer one by its actual dependencies. Preserve existing specialist interfaces, full applicable instructions and host-native execution and permissions. Keep role, model and provider selection under TEAM and the host's settings. Add no model-specific reasoning suffix, compulsory tool stack, extra approval gate or automatic independent review.

Within CORE's one integrated review, follow the drafted prompt as its executor: identify the available input, permitted next operation, resulting artifact and evidence that establishes completion. Compare it with the original request and adopted answers for omitted conditions or added work. Use CORE's existing verification policy for the described work. Return the ready-to-copy prompt first, with explanation when requested. Completing the prompt does not establish that its described operations ran; perform those operations through their specialist only when execution is also authorized.

## Connect the current case

Restore the original request, accepted specification, role, authority, current argument and existing state. Locate the decision-maker's objective and binding constraint, then use DECIDE and econ-design to derive the economic comparison that selects the intervention. Make a consequential model explicit through its actors, feasible choices, information, incentives, timing and response or equilibrium conditions. Solve the defining choice or boundary and acquire the observations needed to decide it. A settled operation proceeds directly to execution.

Use one source-bound argument for the question, current answer, supporting propositions, economic model and evidence. Use existing state tasks for owners, authority, dependencies, actual outputs and completion. The summary presents the current answer, required decision and next result; the story explains its supporting relations; the workplan identifies the tasks that resolve those propositions. Derive these views from the same sources.

When the case has a bound request/specification, use the existing state analyze/converge and requirements mapping for its task, artifact and operation coverage. An allocation changes order within those required tasks; it cannot remove a requested deliverable, change the adopted model or replace completion evidence.

For a requested persistent project view, bind the existing argument graph and source catalog with the management definition through [state](../../../harness/state.md#project-work). `project-bind` retains source identities; `project-view` derives summary, story, workplan or forecast; `project-impact` locates affected tasks and outputs. An existing external Issues/Projects/Jira/Notion record retains its organization's official assignments and decisions. Use that service's available authorized operation for a requested update and record its actual return in the existing task.

## Complete the assigned contribution

Read the current case answer, assignment, adopted model, relevant completed outputs and the dependency the contribution resolves. Select the concrete calculation, comparison, source investigation or artifact that completes that assignment. Fix its population, units, input versions and acceptance condition from the adopted specification. Use existing evidence and results whose producing inputs still match.

Carry the contribution through research, calculation and the requested output. Explain the resulting change to the parent's judgment and supply the actual file or result version its next task consumes. A consultation identifies the unresolved decision and the evidence the authorized person needs. When new evidence changes the assigned result, revise its affected consumers and retain current unaffected outputs.

Use actual work, received feedback and the finished result to explain a requested improvement in the user's practice. Show the next concrete action that improves problem selection, analysis, explanation or execution in that assignment.

## Manage the case

Derive the intervention from the case's economic objective and mechanism. Link each necessary proposition to its evidence, executable work, responsible actor, available information and downstream use. Choose the next task by its effect on the final judgment or feasible action relative to its resource and delay cost under DECIDE. Assign coupled judgments to the lead and bounded implementation or fixed extraction through TEAM.

For a new case, establish the purpose, success criterion, decision right, fixed constraints and requested outputs from the actual sources. For an inherited case, preserve adopted decisions and existing calculations. Use the argument graph to state the current answer and its inference. Bind the work to that graph in the existing state; retain externally approved commitments at their actual source.

Select a division of work from the contributors' capabilities, information, incentives and the cost of briefing and integration. Preserve one writer per shared target. Compare the feasible solo and team outcomes through the same task and completion condition. The principal-agent, multitask and decision-rights models in CONTRACT-01, CONTRACT-07 and CONTRACT-08 can determine effort and information responses; CONTRACT-05 and CONTRACT-09 connect joint production to coordination and specialization.

## Resources and dates

State effort, service duration, resource units, capacity, release times, dependencies and costs in declared units. Include the existing use of shared people or equipment. An allocation consumes the capacity it actually requires. Compare its changed final outcome, displaced work, direct cost and deadline loss through the adopted economic objective. Use the specialist's optimization interface when the requested allocation requires solving an optimization model.

The existing `project-view --view forecast` computes a resource-feasible schedule under the adopted priority order. Repeat `--priority TASK` to compare a candidate global order and use `--capacity JSON` for proposed resource capacities. Neither proposal changes state or establishes actual capacity. Compare task and project finish, precedence-only critical paths, resource waits, remaining and total planned direct cost, and target/approved date delays. Evaluate deadline losses and displaced work through the same economic objective. An information action's value is the improvement from decisions made after its possible results; do not count that improvement again as direct value or avoided rework. Use supported orderings and switching conditions when numerical inputs are absent.

Save the adopted allocation as the existing `project_judgment` object output, with evidence, actual actor and target, current project bindings, selected order and economic rationale. The state contract validates the existing allocation decision rights and feeds the judgment back into forecast. Shared portfolios require authority for each affected project. Summary/workplan return the selected order and resource-feasible next tasks; each contributor receives its argument propositions, inputs, output/action requirements, current output identities and next action. A forecast candidate supplies a comparison; adopted authority and fixed commitments still govern execution.

Preserve approved commitments, target dates, the calculated forecast and actual dated events in their returned fields. An observed delay changes its affected duration, capacity or release condition through the authorized versioned plan. Solve the resulting dependency and cost consequences, compare feasible recovery actions and implement the selected authorized change. MATH-04, MATH-07 and MATH-09 give the allocation and capacity models; INFO-02 and DYN-07 support consequential information and waiting decisions.

## Change and recovery

Locate the exact new evidence or actual decision, the premise it changes and the work that consumes that premise. Use `project-impact` and existing output dependencies to identify affected and reusable results. Its resource, work-timing and deadline selectors locate schedule reassessment separately from scientific output invalidation; `--project` includes competing portfolios. A changed plan binding or determining evidence removes an old judgment from the current allocation. Revise the economic comparison, selected action and affected tasks together. Apply the authorized requeue, input, output or context update through the existing state and research paths, then regenerate the dependent artifacts.

Use the argument's selected owner references and `project-impact --references` for knowledge, original propositions, evidence claims, actual inputs and result consumers. Select the returned review, recalculation, regeneration or authority action through DECIDE. An updated source justifies reassessment; adopting a different estimand, identifying assumption or model still uses its actual decision right. A display change regenerates its artifact while retaining estimates. A changed consumed input selects its own estimate and dependent exhibits. Keep unrelated knowledge and current results reusable. The manager's derived views carry this same dependency result to the contributor; they create no new assignment or permission.

Keep the preceding plan and argument at immutable versioned paths. A changed project binding uses the actual authorized amendment evidence; its previous and replacement hashes identify the adopted change. A proposal remains a proposal until its required decision occurs. Prepare that decision's options, economic effects, costs and execution consequences for the authorized actor. Source drift is reconciled before dependent work resumes.

For an execution failure, compare the actual command, inputs and error with the producing code. Repair that cause, rerun its affected operation and inspect the requested output. Recover from interruption with the bound original request, current project definition and argument, authority, actual outputs and next operation. The existing hook restores the full project sources when its host supplies that boundary; obtain their complete bodies before continuing.

## Discussion and interviews

Choose a discussion or interview to resolve an actual premise or decision. Identify the deciding actor, the information each participant can supply and the comparison that separates the relevant explanations. Prepare the evidence and questions in the order needed to reach that decision. For an interview, link each question to the model quantity, behavior or institutional fact it can establish; seek concrete actions, dates, examples and contrasting cases.

Retain the actual response, attribution, date and source version through econ-literature. Connect qualitative findings to the observation or mechanism they establish and compare opposing evidence on the same object. Infer a person's preferences or incentives from actual evidence and the adopted model. Select a further observation when it changes the resulting decision.

After discussion, extract the actual decision, actor, assigned work, agreed date and changed condition. Preserve proposals and reported facts at their actual status. Apply the authorized change to the argument, task inputs, capacity plan and artifact, then complete the affected operation. The returned result advances the case's decision and work.

## Contact drafts

Prepare the intended recipient, purpose, timing, decision or information requested, supporting material, questions and complete message. Give the authorized user the finished draft and the judgment it enables. Keep email, chat, invitations, reminders and notifications as drafts in this operation. A user-selected external communication requires that specific sending instruction and the actual destination operation under CORE and EXECUTION.

## Artifacts and integration

Choose the reader's decision and the proposition the artifact must establish. Connect the final answer to its model, evidence, calculations, comparisons and resulting action through econ-writing. Produce the actual report, proposal, figure, presentation or explanation in the requested medium. Use the existing Quarto, LaTeX, Beamer, HTML, PDF, SVG and research-result paths for their formats.

Retain source and statistic identities with each exhibit. A changed result regenerates its consuming exhibit and narrative through the existing dependency owner. Inspect the completed rendered artifact, its quantities and explanatory sequence. Prepare the requested oral explanation and questions from the same results.

Integrate worker returns against their actual assignment, input versions, definitions, units and completed operation. Resolve a mismatched premise before combining its descendants. Retain the parent's final question and authority through each specialist return and complete the original artifact and authorized action.

## Outcomes and handover

Evaluate adoption through the affected users' actual choices, incentives, information, ability, access, workload and equipment. Derive the intervention from the binding condition and compare the resulting behavior and final outcome. Define an adoption measure's population, period, numerator and denominator. Tie the business or welfare result to its actual measured quantity and target.

Record actual judgment, acceptance, handover, outcome and work timing through the existing state object-output contract. The [project state contract](../../../harness/state.md#project-work) binds each observation to its actor, date, evidence and current target version. Check the actual acceptance authority and artifact version; preserve its reported provenance. Inspect the final outcome even when every administrative task is complete.

Complete the deliverables, reusable execution instructions and recipient-facing handover. Identify the actual acceptance, receiving owner, remaining obligations, open work and owner of subsequent outcome measurement. Verify that the next operator can use the supplied artifact or procedure. Keep delivered work, acceptance, operating transfer and realized outcome at their actual recorded states.
