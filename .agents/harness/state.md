# State, consumed dependencies and resumption

Use only when durable state, saved-result reuse or resumption is needed. Inherit [CORE](../runtime/CORE.md) and the [completion contract](../runtime/EXECUTION.md#checks-and-completion). Ordinary answers need no local store.

## State and version contract

Represent this task record in an existing store or conversation when tracking or resumption needs it. The local helper described below implements the file-backed form; ordinary answers need no state file.

- task_id, parent_id, owner: identify the task, parent dependency and one result owner.
- operation_kind: answer, modify, create or external.
- status: queued, running, blocked, completed or failed. This remains the scheduling state; completed never means published.
- stages: read-time completed, self_checked and reviewed assessments on show and inspect, derived from current task data and check receipts.
- blocked_reason: dependency, user_hold, interrupted or permission; present only while blocked.
- read_dependencies: protected inputs and versions that the operation may not change.
- consumed_inputs: the exact direct input versions consumed by each operation.
- after: preceding task IDs controlling start order only; never implicitly consume all their outputs.
- consumes: explicit producer_id, output_id, kind, content_version and definition_versions records; include publication_group_id only for outputs required to be published together.
- required_outputs: requested role, kind (file, message or object) and exact target for each deliverable.
- required_actions: target kind, target identifier and operation for each requested action.
- contract_revisions: retained initial and subsequent requirement snapshots, hashes and source evidence. A new contract does not erase the old one.
- context_revisions: retained governing instructions, adopted decisions and the evidence authorizing their revision, in this same task record.
- outputs: registered role, file/message/object identifier, resulting content version, adopted definition_versions, local producer_id and any required publication_group_id.
- action_results: returned results of performed actions, with target identities, assessed versions and result records.
- write_scope: authorized relative file targets, when applicable; external_targets holds exact external object identifiers separately.
- required_checks: identifiers of the task's applicable checks; empty when none apply.
- check_receipts: check operation, target input/output versions, result and evidence class. Self-checks are separate from candidate-bound worker-result evidence.
- authority, holds, next_action: current scope, preserved stops and the next authorized operation while unfinished.

Use the existing runner's dependency graph as canonical. Record only actually consumed artifacts and meaning-determining definitions such as sample, measurement and estimand. A changed consumed definition invalidates its users even when numerical bytes match. An unused parent output change preserves the child and its matching check receipts. A required publication group binds outputs that must be current together. A skill-index or style-rule version alone is not a numerical dependency; connect recomputation to the inputs, code, definitions and environment actually used.

Record native model-role assignments, Astra's actual attempted core and returned failures, and requested accounting as existing object outputs and their original launch/return evidence. Preserve requested model and effort separately from the host's observed model and effort. The role policy adds no task status, model service or second state store; [TEAM](../runtime/TEAM.md#native-model-roles) owns its assignment and escalation decisions.

Use content hashes to identify file contents; keep path and content identity distinct. Message and object values use SHA-256 of UTF-8 json.dumps(value, sort_keys=True, ensure_ascii=False), with Python's default separators, both at registration and on reads. A stored value/hash mismatch invalidates completion, checks, review and consuming dependencies. Git identifiers may supplement content identity when available; their absence does not make an input unusable.

For an in-place modification, retain the pre-change version as consumed input and the post-change version as output. Do not require the current output bytes to equal the pre-change bytes. Protected read dependencies must remain preserved. A change to a protected input is a conflict to resolve within authority.

## Governing context

The existing task record can retain `task_context` with exactly `request_refs`, `goal_and_constraints`, `active_instruction_refs` and `adopted_decisions`. Register it with `add --task-context FILE`. Request references use source_id, version and content_sha256; instruction references use rule_id, version, section and content_sha256. Each may include a root-relative path whose bytes must match the hash. Versions are nonempty strings or nonnegative integers. Each adopted decision has decision_id, version, choice, reason and switch_condition. Its optional change_authority is fixed by default; use delegated only when the existing task actually authorizes the agent to revise that choice on evidence. goal_and_constraints holds the governing objective and binding conditions. Keep the selected central problem, its value and adopted selection reason in that governing objective and the existing adopted decisions at the needed granularity. Keep current working hypotheses, decisive obstacles and actual results in existing outputs and the next executable operation in next; their ordinary update does not rewrite instructions. This uses the current fields and does not require a new form or a store for a simple response. Reference the pinned common contract among the request records when it governs required outputs/actions; derive the existing required_outputs/required_actions declarations from that contract. The local state record does not authenticate user authority.

`context_id` binds this content, authority, holds, declared requirements/scope and the recorded content hash. Candidates and check receipts share it. It excludes Git display revisions, time, progress status and next-action display text. `outputs`, `consumes` and `next` remain the sole completed-result and continuation records. No duplicate completed_refs or next-action ledger is created.

A child's file scope and external targets must fit every ancestor's assigned bounds. Omitted authority and task context inherit from the parent; an explicit child declaration still retains the ancestor constraints. `effective_constraints_sha256`, `effective_holds` and `inherited_authority` are derived from the setting tasks and bind the child's candidate and check context. Check them again at start/resume and before accepting current results. A changed applicable parent hold or governing context blocks an active/completed child, invalidates its assessments, and preserves its output bytes. An unused parent output or an unrelated scoped hold does not invalidate the child. Parent context changes propagate to children that inherited that context; explicit child context remains subject to the current ancestor context.

Resume compares record bytes, retained context, revision evidence and current referenced content. A changed context or record blocks resume and old assessments; outputs remain saved. Restore the original request and applicable instruction bodies from their retained references after context compression or transfer; a summary is an index to those sources. Stop the active task, reconcile an authorized context change with `set-context ID --task-context FILE`, or use requeue to refresh a changed substantive record. Recheck affected judgments against preserved outputs. A prose-rule/context update alone does not remove numerical results or alter consumed numerical definitions. Numerical recomputation follows the existing input/definition dependency rules. Current context can be supplied to start/resume with --task-context; a different governing version must first be registered. Permission/user holds still require the existing explicit release-hold operation.

`set-context` retains full revisions in the existing state. Rebinding identical content or adding a reference or decision preserves the previous instructions without additional authority evidence. Removing or replacing a request, applicable rule, fixed decision or governing objective requires --user-change FILE. Use the existing user-change shape below with previous_context_sha256 and replacement_context_sha256 over the complete old and new task_context objects. This records an instruction already given; it does not require asking again for authority the user already granted. Compare the saved instruction with the actual conversation and its scope. Changing a local path while retaining the same source identity, version and content hash does not change authority.

Revise a delegated decision within its unchanged switch_condition with a new decision version and repeated --decision-update JSON records, one per changed decision, containing exactly decision_id, reason and evidence (existing root-relative result paths). Read that evidence and establish why the stated switching condition now holds. The helper binds its saved bytes and rejects missing evidence; it does not infer the economic conclusion. Deleting a decision, changing its switching criterion or converting a fixed choice to delegated requires the bound user instruction. Preserve the original analysis versions used by earlier revisions. Changed revision or evidence bytes invalidate current assessments, while saved output bytes remain available for reconciliation.

Older receipts lacking context_id cannot establish a current context-bound check; retain their outputs and obtain only the missing assessment.

The existing hook restoration includes the bound task and ancestor governing contexts, their adopted decisions, original request/specification and instruction bodies, required outputs/actions, saved result references and next operation. It restores task and ancestor object/message values with their locators, versions and current/stale status; identical values are included once. These saved hypotheses and results are evidence, and the original instruction and decision authority still govern their use. Source bodies are checked against their recorded hashes and included once per identical content. For structural research, bind the canonical model specification as a request/source reference and carry its revision through the consuming estimates and counterfactuals. Ordinary progress and reusable numerical experience stay in existing outputs and continuation records; they preserve the binding source and its change authority.

```

Declare requested deliverables in this same command with `--operation-kind`, `--authority`, repeated `--required-output` and `--required-action`, using the state helper's role/kind/target and target_kind/target_id/operation records. File outputs need their producing actions; the final response is retained as a message requirement. Exact object and interactive-input authority uses repeated `--external-target`. The existing context owns this minimal completion contract; no state store is created. A simple response needs only its selected operation and actual final message.

The explicit command records selection, the resolved contract, rule/skill closure and source hashes. Repeating the same binding preserves its bytes. Removing a declared output, action or external target requires the existing `--user-change` evidence; additive requirements preserve the earlier contract revision. A source, request or selection change follows the task's existing authority and explicit rebinding. A later durable state binding must retain the declared requirements and authority. Tasks using the state helper retain their full request and applicable instruction references through `task_context`. In ChatGPT Cloud, use the available state, file and native-agent paths to restore those sources after context loss. Local hook installation configures the clients that load it.

For ordinary completion, the hook and state helper share the required-output/action predicate. The hook checks actual callback outcomes and current saved-file hashes, rejects failed or missing required work, and waits for child returns to reach the parent. Needed mutation callbacks and enabled execution observations are stored once in the existing preflight record; context and restoration carry their hashes and locators. Unused ordinary read records are omitted. Compact/resume reuses the saved result when its bytes and authority remain current. The same completion contract applies to each task; actual returned actions and current artifacts establish its result without a separate publication certificate.

The existing reinjection record retains policy verification against the manifest, operation closure and each actual file's device, inode, size, modification time, change time and mode. Every callback checks these identities and rehashes changed files. Permission, prohibition, target, hold and current-result checks still run for each operation. Task entry, changed instructions, failure, compaction, recovery and delegation deliver the complete applicable bodies and original request; stable ordinary callbacks reuse them without another common reminder. A cached verification records file validity and never asserts model reading.

The registered `PreCompact` handler validates the saved request, selection and bound task through existing owners. `PostCompact` records pending restoration in the existing reinjection record. Both use the host's common stop/message contract. `SessionStart(source=compact)` delivers the full restoration and clears the pending state. Keep exact host event/trigger identities and the actual spill-file locator. Read the complete original request and required rule bodies from their saved sources before dependent work; a callback, saved snapshot or reading receipt supplies no omitted text.

Compaction pending state is associated with the root or actual child `agent_id`. On a host whose compacting child continues through `PreToolUse` or `Stop`, that existing event first denies the tool or blocks completion and returns the full governing text. The owner reads the required sources and reissues the authorized operation. A root SessionStart consumes its own pending state. Child restoration retains the exact observed successful native spawn call and return in the existing child record, with its source hash, original assignment and parent context.

Child-dependent writes and completion stay held during this recovery; reads, parent communication and existing state/source recovery continue. Restored sources retain their actual authority, holds and versions, and callback provenance remains recorded as observed evidence.

## Project work

Use the existing task store and [argument engine](argument.py) sources for requested persistent project work. `project-work:contribute` and `project-work:manage` select the user's role; ordinary one-step work continues through its existing specialist.

```sh
python .agents/harness/state.py --root PROJECT project-bind CASE --definition plan-v1.json
python .agents/harness/state.py --root PROJECT project-view CASE --role contribute --owner PERSON --view summary
python .agents/harness/state.py --root PROJECT project-view CASE --role manage --view story
python .agents/harness/state.py --root PROJECT project-view CASE --role manage --view workplan
python .agents/harness/state.py --root PROJECT project-view CASE --role manage --view forecast --project OTHER_CASE
python .agents/harness/state.py --root PROJECT project-impact CASE --node CLAIM_ID
```

The definition has `schema_version:1`, `argument:{path,sources_path}`, `resources`, `work`, `priority`, `data_date_hour`, `time_unit:"hours"`, `origin`, `target_finish_hour`, `approved_finish_hour` and `decision_rights`. Optional `budget` and resource/fixed costs use a declared `currency`. `origin` is an ISO timestamp with timezone or an explicit `relative:LABEL`. Each resource maps its ID to `capacity_units` and `hourly_cost`. Each work row supplies an existing descendant `task_id`, determining `node_ids`, positive `duration_hours` and required resource units; optional `release_hour` and `fixed_cost` preserve their declared meanings. Priority names each work task once. The argument and source catalog use their existing source-bound contracts. Keep the question, answer, model and evidence there; keep owner, status, authority, dependencies and produced versions in the task store.

Binding stores exact definition, argument and source paths and hashes. Repeating it preserves its bytes. Keep preceding sources at immutable versioned paths. A changed bind requires `--user-change` with the actual source, message ID/text, `previous_project_sha256` and `replacement_project_sha256`, computed with the existing `content_hash` on the old and new binding objects. Stop an active task before changing its adopted binding. A revised completed parent is blocked for its affected reassessment with its outputs preserved. The project binding affects its owner's context; selective consumption and `project-impact` retain reuse of unaffected child results. Source and amendment-evidence drift feed the existing resumption and ancestor constraints.

The views derive the current summary, argument story and workplan from this same binding and state. Contributor views select the named owner's work; manager views include the case's decision rights and shared resources. Work rows connect their actual argument propositions, input/consumed-output versions, required outputs/actions, current output identities and next action. Their priority rank and schedule come from the same forecast. `next_tasks` identifies work whose dependencies, release and resource slot permit continuation at the data date; completed work is reused. It grants no execution permission.

`forecast` computes a feasible schedule under the selected priority, precedence, release, data-date and resource constraints. It reports the precedence-only critical path, resource waits, resource units, remaining/total planned direct cost, budget and approved/target/forecast/actual times, including target and approved-date delay hours. Running work retains its resource slot ahead of unstarted work in `execution_order`; a new proposed priority cannot preempt it. An unresolved predecessor is blocked. Shared projects require matching origins, data dates, currencies and common capacities. Repeat `--project CASE` for the portfolio in forecast, summary or workplan. Repeat `--priority TASK` for every selected task to compare a candidate global order; `--capacity '{"RESOURCE":2}'` compares proposed capacities. Proposals use the same scheduler without changing sources, saved priorities, authority or actual capacity. Deadline losses and the opportunity cost of displaced work belong in DECIDE's economic comparison; elapsed time and money are not combined into a generic score.

Use existing object outputs for actual project observations. Supported roles are `project_judgment`, `project_acceptance`, `project_handover`, `project_outcome` and `project_actual`. The value records `actor`, `date`, `status`, nonempty `evidence:[{path,sha256}]` and `target`. An artifact target is `{task_id,output_id,content_version}`; an argument target is `{node_id,argument_sha256}`, using `argument.argument_sha256`. Current sources and artifact versions determine which observations enter the views. Actual acceptance/handover must name the actor in `decision_rights.acceptance` or `.handover`. Preserve the actual evidence's provenance.

Judgment status is `supported`, `refuted` or `proposed`; acceptance is `accepted`, `rejected` or `proposed`; handover is `handed_over`, `rejected` or `proposed`. An outcome records `observed_value`, `unit`, `target_value`, `comparator` and `observed` or `proposed` status. Actual work timing records `start_hour`, `finish_hour` and `actual` or `proposed` status against its task output. A completed task retains its scheduling meaning. Assess the target outcome and actual acceptance from their respective evidence, then perform the required next work.

For an economic allocation decision, extend that existing judgment's value with `allocation:{project_bindings,priority,rationale}` and an optional nonempty `switching_condition`. `project_bindings` maps every selected project ID to `content_hash(binding)` from `project-bind`; `priority` names all selected work tasks exactly once. Record the same objective's outcome comparison, information value, costs, displacement and assumptions in the rationale and its existing evidence. Do not add an information-induced improvement a second time as avoided rework. Use existing consumed-output dependencies for determining results and retain the current argument target. Numerical inputs need their actual source; a supported ordering or switching condition can select the action without invented numbers.

Only a current `supported` judgment from the actor in `decision_rights.allocation` changes the default forecast. For shared projects, matching judgments must establish the allocation rights of every affected project; a common authorized actor can cover its projects in one record. A proposed judgment never adopts an order. Conflicting supported allocations require the authorized decision; replace the existing judgment output through its normal versioned path. Changed plan bindings or determining evidence require reassessment. With declared allocation rights and no current adopted judgment, the view returns `decision-required` and no next tasks. Legacy plans without allocation rights retain their explicit baseline priority. This ordinary recorded authority does not authenticate an external mutation or change user-fixed specifications or commitments.

`project-impact` joins argument change propagation with task and consumed-output dependencies, returning affected and reusable task/output identities. Use `--node CLAIM` for a changed proposition, `--resource ID` for changed capacity, `--task ID` for a work-timing change, or `--deadline` for changed dates; at least one is required. Repeat `--project CASE` to include sharing portfolios. `schedule_task_ids` includes competing resource users and dependent work, while `affected_outputs` identifies scientific results whose actual argument/output dependencies changed. Capacity or deadline changes alone do not invalidate valid scientific outputs. Apply an authorized change through the existing context, requeue, input, output and research commands, compare the revised forecast and update the existing judgment when its decision changes. The impact query keeps the state unchanged. Root and child hook restoration include the complete current definition, argument and source catalog from the existing project binding, once per content hash. Their emission retains the full-reading obligation.

Argument nodes can use `references:[{kind,id,path,version,relation,basis}]` to join existing owners at read time. `knowledge` selects a knowledge ID and its true prerequisite bodies and conditional application relations through Reader; `literature` selects an original corpus proposition and verifies its original locators; `claim` selects the existing evidence contract's current claim fingerprint. `file` binds bytes, `json` adds the existing nonempty `keys` path for a selected value, and `output` uses the producer task ID as `path` and its output ID as `id`. A selected artifact-registry value also binds its actual producer references, even when a recomputation returns the same value. Versions are the returned content identities, never a copied entity or a second store. Paths are project-relative. Knowledge `path:"@package"` reads the executing package's own collection; use the existing econ-knowledge owner bundle's state helper when its conditional collection is packaged separately. The other owners remain at their registered code paths.

`project-impact CASE --references` compares those identities. Reference relations `supports`, `refutes`, `assumes`, `prerequisite_to_understand` and `requires_to_apply` request review; `execution_input` requests recalculation; `generated_from` requests regeneration; `adopted_specification` requests authority. `related`, `alternative` and `alternative_under` remain reference-only. Optional `when:{decision_id:[accepted_choice]}` uses the current adopted decisions in governing context. Missing conditions or inputs require a decision/input, and a mismatched condition is inapplicable. Existing argument dependencies can add `effect:review|recalculate|regenerate|authority|reference` and the same `when`. Their direction remains prerequisite to consumer. The existing impact traversal propagates these effects; review or missing authority cannot silently become recalculation or regeneration. It returns `node_actions`, `unresolved_conditions` and task `actions`, alongside existing affected/reusable identities. For an actual known node change, repeat `--change NODE=ACTION`; an untyped legacy graph retains its existing impact API.

Summary, story, workplan and forecast expose these selected dependencies as `reference_impact` and hold work requiring authority. Analyze joins the same impact into affected task findings; Converge consumes that analysis. Completion checks the same selected references for the task and its bound project, rejecting unresolved changes without adding a review plan. A related-reference or bibliographic metadata update supplies no numerical dependency. A changed result follows its actual output consumers; `after` remains start order. A work row can declare the adopted `effect` for a consumed result. A consumer lacking a typed argument edge or work effect requires the owner's decision instead of assuming it is an estimate or an exhibit. Read the classified action and its current reference before choosing review, requeue or artifact generation. A reference query never edits an adopted model, project binding, task, output or permission. Reuse valid estimates during a source review. Adopt an authorized changed specification through the existing versioned project/context binding, then requeue only the affected outputs and record the actual new results. The existing full project restoration retains these references, the original request, fixed decisions and preceding source versions.

## Resumption and migration

Restore saved artifacts and compare their versions and governing definitions. Recover the last consumed input and output identities before deciding which work remains. Preserve original records and outputs. Read [State migration](../../docs/ai/integration.md#state-migration) only for a requested migration.

For a formerly completed task with no recoverable assessment target versions, preserve its outputs and perform only missing required checks against identified current versions. Do not rerun the original calculation merely because its old record lacks receipt metadata. Respect holds and use [TEAM](../runtime/TEAM.md#resumption) for active assignments and continuation context.

## Local state helper

harness/state.py manages task records in the selected root. The active runtime executes worker and tool actions; state commands register their returned results. The selected host or existing producer writes the requested output at its authorized destination. Use an explicit --root or the current working directory. Git is optional. Keep its local store and transcripts out of shared artifacts.

For an authorized store operation, read the helper's --help for the command. Its schema-v5 interface records these distinctions:

- add accepts --operation-kind answer|modify|create|external and one or more --required-output JSON records with role/kind/target or --required-action records with target_kind/target_id/operation. Declare requirements from the request before producing results. --record is optional. Repeated --input values identify direct consumed sources; --after records start order only. Repeated --consumes JSON records bind specific upstream outputs using producer_id, output_id, kind, content_version and definition_versions, plus publication_group_id when joint publication is required; --read-dependency identifies protected sources. --required-check defaults to empty. Carry authority and identified holds; use --external-target for opaque external IDs independently of relative file scope.
- output records a file path by default. --role associates it with the declared requirement; an omitted role is inferred only from an exact unambiguous kind and target. --kind message|object with --value records the named result and content identity. Use --definition-versions JSON for meaning-determining definitions, --publication-group-id for a required joint group, and --producer-id for a local producer label (default: task). Use repeated --dependency JSON pairs [producer_id, output_id] to narrow the consumed edges of this result, or --no-dependencies for a result independent of task consumes; omission binds all task consumes. Supplementary progress outputs do not satisfy another role or kind.
- action records an already performed operation using --target-kind, --target-id, --operation, --result and --evidence. A passing object action imports the native returned-tool record from that evidence file and derives its outcome through the existing native adapters. File targets retain their actual content hash, or their missing state for a deletion. Object targets require a registered object output or --target-version from the returned result or readback. Returned GitHub commit and plugin release identifiers must match an explicit target version. Freshness refers to the latest registered result; obtain remote updates through the authorized service and register their versions. Match the declared action target and operation and retain its input/output and result-record versions.
- verify without --worker-result records a self-check using --check, --result and --reviewer; --evidence is optional for a self-check. A name and passing verdict cannot establish independent review. --worker-result FILE imports the structured returned record described below and derives the verdict from its decision. An optional --result must agree. --independent-review tasks require this evidence and its recorded runtime-source match for every required check. All receipts bind current input/output versions; --input and --output can narrow self-check targets so unrelated results retain their receipts. Worker results also bind the complete candidate and become stale when it changes.
- transition completed applies to a running task whose required outputs, actions, versions, dependencies and checks match and whose holds are resolved. The legacy evaluating and interrupted names map to running and blocked.
- resume retains saved outputs and attempt history. requeue --output ID or --producer ID selects the affected branch for recomputation after changed dependencies, preserving unaffected outputs and receipts. Repeated --consumes records replace its upstream input contract and narrow legacy compatibility groups; --no-consumes explicitly clears that contract. A completed task accepts requeue only with an explicit output, producer or consumes selection. For a blocked or failed task without output or producer selectors, requeue removes results stale by bytes or dependencies and preserves current results. A changed check log can be resolved by resume and the affected check without recomputing outputs.
- release-hold requires --hold-id, --authority, --user-release FILE and --next. The saved user instruction has source `user`, nonempty message_id/text and the matching source_task_id/hold_id. Release a hold only on its setting task; a child cannot release an inherited hold. Retain other holds and the original general authority. The coordinator compares the retained instruction with the actual user message; local JSON does not authenticate it. A permission/user-hold transition must identify its hold. Optional repeated --hold-operation and --hold-target values on add/transition narrow its application; targets use `file:relative/path` or `object:exact-id`. Omitted selectors preserve a task-wide hold. After the setting task releases an applicable hold, resume the same child and obtain only its invalidated checks.
- set-contract appends a requirement revision for a queued, blocked or failed task and associates preserved exact results with their declared roles. Additive requirements need no user-change record. Removing or replacing any existing output, action or external target requires --user-change FILE with the exact user instruction and old/new contract hashes. An omitted old requirement is a removal, not implicit permission to drop it. The helper retains the prior snapshot and supplied evidence; it cannot decide whether the quotation really authorized the change.

### Returned action evidence

For a passing object action, save one existing native `action_results_verified` record as the evidence JSON object. Include `event_id`, `operation`, `target`, `status: "success"`, `tool_name`, distinct `tool_call_ref` and `tool_return_ref`, exact `call_args_text` and `return_text`, their UTF-8 SHA-256 values in `call_args_sha256` and `return_sha256`, and the existing `source_verification` runtime-match record. Match the saved bytes and references to the host's actual call and return. The [native operation parser](native_check.py) supplies the registered tool/operation pairing, exact target, error handling and command continuations. The state receipt stores its normalized `operation_outcome` in the existing action record.

Use `github.update_ref` with `mcp__codex_apps__github_update_ref` and target `owner/repository:refs/heads/branch`; use `plugin_creator.update_plugin` with its same-named MCP tool and the existing plugin ID. Command actions use `execute_command` and the exact initiating command string. Register the command's actual `write_stdin` continuations until the terminal result. Nonempty input also requires the exact external target `stdin://SESSION/SHA256`, with SHA256 of the UTF-8 chars; polling uses empty input. If the live session identity requires additional authority, block the task, add the exact target through `set-contract`, then resume the same task and process. Re-register its retained returns under the current contract rather than rerunning completed work. A terminal session cannot accept further input or polling. A nonzero exit, returned error, mismatched target, conflicting result branch or running session prevents a passing receipt. Keep a failed operation's return with `--result failed`, repair its cause and register the completed replacement. Existing stored receipts retain their recorded versions; new passing object receipts use the returned-tool contract.

### User-directed contract changes

The user-change JSON object contains source equal to user, a nonempty message_id, the verbatim user text in text, previous_contract_sha256 and replacement_contract_sha256. Both hashes use the JSON encoding above over an object with required_outputs, required_actions and external_targets. show exposes the current contract_revisions snapshot and hash. Array order is retained. Retain the actual user message in the task conversation and compare the saved quotation, identity and scope change with it before importing; hashes bind versions, not authority. A fabricated user label is not authorization.

Revisions retain their complete snapshots and the change file hash. Missing or changed saved change evidence invalidates the contract's current completion assessment. Pre-existing stores without revision history retain their legacy semantics; their first set-contract change records the previous snapshot before appending the new one. Already existing requirements are never inferred from preserved outputs.

### Worker-result evidence

The JSON passed to --worker-result preserves the original return and its runtime references:

- The envelope contains role equal to --check, worker_id equal to --reviewer, distinct launch_ref and return_ref, execution_status equal to completed, return_text, return_sha256, and source_verification. The worker differs from the task owner.
- return_text is the exact original structured JSON object, with schema_version equal to 1, role, candidate_sha256, decision, findings, unassessed, errors and checks. return_sha256 is SHA-256 of its raw UTF-8 text.
- candidate_sha256 uses the JSON encoding above over candidate(task), including task identity, owner, versions, required outputs/actions/checks.
- decision is pass or fail. findings, unassessed and errors are arrays. A pass requires empty arrays, checks[role] equal to passed, and every reported check equal to passed. Preserve resolved finding history in a separate original-object field.
- source_verification has status matched-to-runtime or not-verified. A matched record includes verifier_id and reference identifying the coordinator's actual runtime comparison.

The importer derives the verdict, arrays, checks and candidate reference from return_text and stores that object as worker_result.normalized_return in the receipt. Compatibility copies of substantive fields in the envelope are optional and must match the original JSON exactly, including types. The original evidence file and return_text remain intact. A fail in the original and pass in an envelope or --result is rejected. Missing original fields, duplicate JSON keys, nonfinite values and unstructured legacy returns require a corrected structured return before review registration.

The helper re-parses the saved original on reads and compares it with the normalized receipt, file hash, current candidate and task checks. Changes invalidate the current receipt. Terminal state, role, worker identity and distinct launch/return references are checked across required roles. Source status not-verified remains self-reported and cannot satisfy --independent-review.

The coordinator compares worker references with actual runtime launch and return events. State candidate(task) digests and native-check file-byte digests identify different objects; retain both and their mapping. Tests exercise synthetic saved records.

Use explicit capacity, depth or attempt limits only when the user or runtime supplies them. For a requested legacy-store conversion, use [State migration](../../docs/ai/integration.md#state-migration).

## Find saved work

Use `.agents/harness/state.py find QUERY` when the task ID or saved result is unknown. It reads the existing local store and returns candidate IDs, recorded status, owner, immediate parent, matching JSON pointers and short excerpts. Whitespace-separated terms use case-insensitive literal matching; all terms must occur somewhere in the same task. Japanese terms remain searchable without translation. Search covers recorded context, output and evidence references, action results, checks and retained history. File bodies and external services are not searched. A former failed check can match a task whose later check passed; read the pointed original before deciding what that failure means.

Narrow candidates with exact `--parent`, `--owner` or `--status`; parent selects immediate children, and status selects the recorded scheduling state. Pages are ordered by task ID. `--limit` controls the number of candidates (default 5); `--offset` selects the next page. Pass the returned `store_sha256` with `--snapshot` when continuing a page sequence so a changed store causes a fresh search. Each candidate includes at most three matching excerpts, the full match count and the number omitted. These are navigation excerpts; the original source bodies remain intact.

Select a candidate with `.agents/harness/state.py show ID`, follow its request, instruction, adopted-decision, result and evidence references, and restore the complete applicable source bodies. The returned pointers address the helper's existing normalized task record; request/rule/decision references retain their original identities, content versions and paths in that record. Use existing show/resume/version checks to compare the current request, inputs, targets, definitions and holds before reusing the result or continuing an operation. A search hit and its recorded status do not certify completion, freshness, permission or applicability. The locator command does not acquire the writer lock, save migrations, replace instructions or create another memory store.

## Local assessment stages

The verify command compares saved task records, candidate versions and check receipts. Use CORE for the integrated review and EXECUTION for actual destination completion. show (one task or the entire store) and inspect expose these assessments:

- completed: the completion contract, results, dependencies and checks are current and holds are resolved. Scheduling and upstream consumption use the status and dependency rules above.
- self_checked: current caller-recorded checks cover every output and required check. Receipts with unchecked worker-source references remain in this class.
- reviewed: distinct passing worker-result records have recorded runtime-source matches and bind the complete current candidate. They cover every output and required check. review_source is worker-result-evidence, and missing_independent_checks lists required checks without current matched worker evidence. An empty evidence set does not establish review.

Changes to candidate bytes, definitions, requirements, source dependencies or saved check evidence invalidate the affected assessment. Holds also apply. Older receipts without candidate binding retain ordinary completion and reuse behavior but do not establish self_checked or reviewed.

Schema-v5 migration preserves tasks, outputs, contracts, dependencies, check receipts, action results and holds. It discards retired publication records and saved stage flags from the task and its history. Read-only commands derive the migrated view; the next state-writing command persists it. Prior publication records do not establish worker review.

Publication completion follows the actual returned operation and current destination version. The state helper retains the corresponding action result and current artifact dependencies.

## State writer ownership

State updates hold a nonblocking exclusive OS flock on one persistent .lock file from read through atomic save. The descriptor remains open for the update and is closed afterward; process termination releases ownership automatically. Keep the lock file in place so every writer uses the same inode. A competing live writer returns the state path and a retry instruction. Resume from the last complete JSON after the writer exits; never delete and recreate the lock file to bypass a live writer. Save through a newly and exclusively created private temporary file, flush its bytes, then replace the store and flush its directory. Existing temporary-name symlinks and hard links are never opened. The explicit root write scope `.` contains repository-relative descendants and overlaps every descendant write scope.

## Scoped check coverage and requested deletion

Required checks may be ID strings (each applies to every requested target) or {id, targets: [...]} records. Keep scoped receipts per check and target; each required pair needs a current passing receipt. A later current failed verdict shadows an earlier pass for that pair. Changes invalidate only affected target receipts and their actual dependencies. All requested targets must be covered before completion.

For a requested delete/remove/unlink action on a consumed input, bind its input_version to the pinned pre-deletion file hash, actual operation and target, successful evidence and observed absence. This tombstone permits only that requested deletion through input validation. Recreating it or changing another consumed input invalidates affected work; explicit read dependencies remain fixed.

## Analyze and Converge

Use this path for requested specification consistency or implementation completion reconciliation. The ordinary task contract continues through its existing output, action and selected check requirements. An adopted version-2 [requirement contract](requirements_check.md#analyze-an-adopted-implementation-specification) adds the explicit traceability array for this path.

Bind that contract and the original request when adding the task with `--requirements REQUIREMENTS --request REQUEST`. An existing queued, blocked or failed task accepts the same pair through `bind-specification`. The binding retains exact file paths and SHA-256 values in the task's `specification` and its revision history. Replacing an adopted binding uses the existing `--user-change` evidence with `previous_specification_sha256` and `replacement_specification_sha256`. Keep the preceding source files and instruction versions available.

```sh
python .agents/harness/state.py --root . bind-specification TASK \
  --requirements .agents/state/TASK/requirements.json \
  --request .agents/state/TASK/request.txt
python .agents/harness/state.py --root . analyze TASK
python .agents/harness/state.py --root . converge TASK
```

Analyze reads the current requirement contract, governing decisions, task inventory and mapped implementation bytes. It reports uncovered requirements, unresolved or cyclic prerequisites, contradictory explicit constraints and predicates, missing code/check declarations, changed decision pins and task/scope correspondence. Requirement IDs select existing task IDs and declared checks; mapped tasks belong to the selected owner and its descendants. The reverse comparison locates task outputs, actions and checks lacking a requirement mapping.

Converge additionally evaluates current artifacts, registered outputs and actual action/check evidence. File artifacts use their current bytes. A declared object output can supply a matching artifact path through its current JSON value, encoded with the existing sorted-key, UTF-8 object identity convention. `message://final` consumes the mapped message output. Each required action retains its original native call and return through the existing action importer. Current dependency, context, hold and scope rules apply throughout the task tree.

A mapped executable check registers its actual command result through the existing verifier:

```sh
python .agents/harness/state.py --root . run-check TASK --check TEST_ID
python .agents/harness/state.py --root . verify TASK --check TEST_ID \
  --result passed --reviewer EXECUTOR \
  --execution-result .agents/state/TASK/actual-command.json
```

`run-check` executes the exact command pinned by `check_commands` under the task's current authority and holds. The check must be declared on the task. Execution inherits the host's standard process and permission controls; no independent Bubblewrap, libseccomp or fallback isolation layer is installed. The existing record retains the actual command, exit status and complete stdout/stderr, captures specification/code/input/output versions before execution and compares them afterward. A failed run retains its observed command or validation cause. An exit-zero command cannot pass after those bindings or versions change.

`actual-command.json` is the [returned-action record](state.md#returned-action-evidence) for the host's `execute_command` invocation of that producer, including exact initiating arguments and every required continuation through its terminal return. The coordinator matches those bytes and references to the actual execution tool. The native parser derives terminal success; verification matches the returned producer identity to the saved local run and its original assessed versions. Importing an earlier passing run after a code change retains that earlier run's versions. A check name or caller verdict supplies no execution. The existing worker-result path retains candidate-bound semantic review. Changes to assessed code, evidence or specification invalidate their affected receipts.

Converge stores findings on the same task and registers stable repair children in the same DAG. Each repair identifies its requirement and observed defect; its continuation states the required implementation, execution or verification change. Repeated reconciliation reuses those children. A passing reconciliation resolves them from the current evidence and restores the parent's completion path through `resume`. Run the affected operation, register its actual replacement result and reconcile again until every adopted condition passes. A clean repeated Converge leaves the saved task store unchanged. The existing completed transition requires current convergence and all original output, action, dependency and check conditions.

## Optional execution controls and observed usage

Use `.agents/harness/state.py optimization TASK status` to read the current task's optional controls. New tasks start with all automatic features disabled: `experience`, `tools` and `loops`. Repository maps and focused displays run through their explicit read-only commands. Enable a measured useful automatic feature through the task's existing authority:

```sh
python .agents/harness/state.py --root . optimization TASK on --feature loops=true
python .agents/harness/state.py --root . optimization TASK configure --feature experience=true \
  --experience-plan .agents/state/TASK/experience-plan.json
python .agents/harness/state.py --root . optimization TASK protect --capability CAPABILITY_OR_PACKAGE_ID
python .agents/harness/state.py --root . optimization TASK off
```

The same task record stores these controls and their governing-context identity. A changed governing context disables the prior configuration until the operator adopts its current settings. `off` returns the optional features to the ordinary execution path. Current authority, holds, required instructions, task outputs, scientific definitions and completion checks continue through their existing owners. Imported observations retain their evidence status; configure controls through this explicit interface. `--clear-experience-plan` removes the configured plan reference.

For capability selection, supply `--inventory`, `--observations`, `--required` and `--protection-manifest` to `candidates` or `dry-run`. All paths are project-relative JSON inputs. The inventory declares `host`, `host_version`, `source_kind`, `complete` and `tools:[{id,package,rare}]`. Declaration-level candidates require `source_kind:"model-request-declarations"`. Each observation declares a `session_id`, `prompt_id`, and `exposed`, `attempted`, `completed`, `indirect` ID lists; a missing observation remains unknown. The required input lists current task dependencies. The task owner assigns their protection categories: `mandatory_instruction`, `read`, `state`, `recovery`, `current_skill`, `current_external_write`, `delegation`. The first four categories require IDs; conditional categories contain the IDs needed by the current task. Each protected ID or package also belongs in `required`.

The evaluator compares ten prompts across two sessions or five sessions; rare capabilities require ten sessions. Actual use, incomplete evidence, required unavailable capabilities and protected IDs suppress candidates. A package qualifies only when each member qualifies. `dry-run` evaluates the supplied evidence with selection enabled and preserves the task store. `apply` currently returns `unsupported-declaration-reduction-unverified`; `restore` returns `not-applied`. Both preserve host configuration and task state. Adopt a setting change only through a supported host operation whose actual model request establishes the declaration reduction, cache cost and restoration behavior.

Import actual app-server notifications or typed usage events through the existing usage command:

```sh
python .agents/harness/state.py --root . usage TASK --jsonl observed.jsonl \

python .agents/harness/state.py --root . usage TASK --jsonl observed.jsonl \

Optional `resources` records event-scoped tool calls, retries, auxiliary calls, failure loops, human corrections and duration; declare `resource_scope:"event"` for attributable subtotals.

Stable event identities deduplicate imports across tasks; conflicting identities, source overlap, missing delta event IDs, an unknown cumulative baseline or a decreasing counter prevent totals for that affected group. Input includes cached input; output includes reasoning output. Unknown counters remain `null`, reported zero remains zero, and cached/reasoning details stay within their enclosing totals. Reported resource subtotals retain their observed coverage. Session completion, current runtime model and subscription allowance consumption follow the actual host returns.

An epoch label records a counter reset; stable producer identity persists across labels. Importing the same stable event or exact legacy source observation under another epoch is rejected. Existing overlapping records remain intact and expose the overlap with affected totals set to `null`. Distinct stable event IDs and distinct recorded reset evidence retain their separate observations. Codex 0.159.2's `turn.completed.usage` emits the latest thread total and uses default zeros when its upstream usage notification is absent; the legacy importer retains cumulative semantics and its existing zero-counter checks. Retain `tokenUsage.last` with `total` when the app-server supplies both.

Keep the standard host compaction settings until a comparable completed-task measurement establishes lower actual total tokens and elapsed time with instruction adherence, correctness and completion preserved.
