# Team execution

Follow repository policy for scope, authority and execution permissions. Use these instructions for concurrent work, task resumption and requested usage accounting. Keep operational records separate from research deliverables. Do not include project plans, progress, stages, decision or adoption status or future user decisions in research text, explanations, annotations or paraphrases.

## Shared work

The existing coordinator owns the whole integrated result: resolve conflicting findings against source evidence, preserve unresolved disagreement and check the complete argument for contradictions, missing dependencies and unsupported claims. Delegate independent work when its expected benefit exceeds coordination cost. Use the verified runtime's available capacity. Count internal and external workers together and reserve capacity for integration and any needed review. Shared generated outputs have one owner; a connected argument retains a whole-output owner.

Give each worker a bounded assignment: task identity and intended outcome, applicable user content and output constraints, authority and next authorized action, relevant dependencies and exact input revisions, acceptance evidence and separate write range. Before launch or resumption, reconcile current assignments with actual running workers; check for the same substantive task, including equivalent outputs in different directories. Intentional replication or independent review must be identified as such. Do not launch a duplicate merely because write scopes do not overlap.

Bind declared ownership to the actual worker/session identifier and observed capabilities in the existing parent record when coordination requires a record. Preserve unknown runtime controls as unknown. Different role names do not establish separate identities or independent contexts; a worktree or recorded write scope does not establish access isolation. This binding records execution facts, not new permissions or a new orchestration layer.

Each worker returns the conclusion or artifact and its version or hash where applicable, direct supporting evidence, limitations, changed paths, execution deviations, unresolved dependencies and current status or resumable next step. Self-checks remain self-checks. The coordinator decides integration and disposition within the user's authority; worker completion does not authorize a new stage or broader scientific choices. Use this contract in the existing assignment and return, without requiring a separate document for a small task.

## Existing operational state

Use the existing task record or store to resume work. Keep scientific choices in the research specification and numerical provenance in generating metadata. Keep the [team_state.py](../scripts/team_state.py) helper's `.agents/state/` store, transcripts and authenticated settings outside common receipts, exports, build contexts and public artifacts.

Maintain one authoritative current checkpoint when coordinating dependencies or resumption: completed and frozen work, valid evidence, unresolved dependencies, applicable holds and the next authorized action. Link historical records rather than treating their earlier status as current authority. Availability of files or capacity does not lift a hold. Preserve original outputs and assessments; a repair creates a linked new version, and a contract correction precisely supersedes the affected provision without rewriting an old freeze.

The helper stores a record locator separately from computation inputs. Add the task record as an input only when its definitions or adopted choices govern the result. Declare a task's write scope before starting it. Mark a task complete only after its output exists and a verification evidence file records a passed result. Preserve attempts and history. On resumption, inspect the saved outputs and run `inspect`. Invalidate tasks with changed or missing inputs, outputs or verification evidence and their affected downstream tasks. Requeue legacy records with an explicit input list or `--no-inputs`. Resume a CLI session by its verified exact ID. The helper enforces state constraints; it does not launch agents or change platform permissions. Read its `--help` for the requested operation.

## Execution and usage

Use the verified runtime authorized for the task, its account allowance and its project environment. Preserve the user's model and permission settings. Switch runtimes only to supply a demonstrated missing function through a verified permitted execution path. Do not infer free inference from package licensing.

### If usage accounting is requested

For requested CLI usage accounting, retain raw JSON events locally. The verified producer's completed-turn counters accumulate across resumed history. Import counters with an explicit epoch and chronological sequence. Start a new epoch after a confirmed reset. Preserve unknown baselines, unclassified resets, missing fields and unverified all-zero defaults as unknown. Input includes cached input; output includes reasoning output. The helper computes deltas in the declared chronological order. Do not present API-equivalent estimates as invoices or accounting records as evidence of research quality.

## Verifying a proposed change

Independent review is conditional: use it when requested or needed for a consequential unresolved judgment or a specified comparison. Delegation alone does not require another reviewer. Controlled comparisons may require sealed artifacts, input restrictions and global release barriers to preserve distinguishable observations; follow their explicit protocol and stop dependent phases on deviations. Do not impose these experimental stages on routine research. Retry ordinary recoverable failures within unchanged authority and preserve the outcome.

Compare representative results on the same task and evidence. Choose criteria independently of the implementation. Preserve the old result and record the scope reviewed. Assess scientific adequacy and whether the intended reader can understand or use the result. Compare effort and cost among approaches that meet those criteria. Examine generalization on another task. Classify feedback used for revision as development evidence. Repair the demonstrated cause, reevaluate the affected result and reuse unchanged valid work. Keep verification status and implementation decisions in the operational record.
