# Native task execution and review

## Task-proportional review plan

Use `strict-reviewed` by default for completed output: independent request coverage, quality A, quality B and instruction compliance. Both quality workers assess every B25–B31/C01–C15 verdict on the complete exact candidate and compare the governing sources. Keep their original results separate until both are fixed; resolve conflicts at the source, then obtain new returns for any revised candidate. The initial reminder assignment is mandatory and starts before substantive child work; it does not replace either quality role.

`direct` retains the author's labeled self-checks for drafting and repair. `focused` and legacy `full` retain their registered draft checks; none grants publication eligibility. Missing workers never select a weaker publication plan. Only the common strict release gate may authorize output after the actual host validates the required actors, events and returns. Schema consistency, hashes and role-name strings establish record bindings, not independent approval.

## Run and capability contract

Pin the operation, original request, v2 contract, authority, sources, profile, templates and policy before drafting. Use [native_run](../harness/native_run.md) `begin`, `submit`, `finalize` through the existing authorized tools. All transitions preserve the same run and fixed inputs. Capability recovery or an actual author replacement is appended using the current `record_sha256`; update affected returns without copying earlier approvals.

Only `strict` with `strict-reviewed` and every release predicate satisfied can publish plugin-owned final files or response bodies. `provisional` requires an explicit recorded user selection and keeps the candidate and failure reasons inside the run's isolated workspace; it never creates a final output destination or returns an approved final body. A later mode or fixed-input change needs a linked new run.

Trusted local hooks bind the original host prompt and current session/turn/run to the candidate. A hook launch request is not an observed start, and observing stdin callbacks is not authenticated independent provenance. For the host-authenticated assurance class, the host-owned verifier must obtain the original request, distinct worker start/end/returns, blind coverage and quality inputs, actual operations and final candidate from its existing trusted event source. No model argument, local JSON, hash, environment setting or self-check creates this authority. If that capability is missing, keep `blocked-unapproved` and identify the missing event and next authorized action. Stop requests continuation; only a host owning final transmission can enforce pre-send blocking.

## Original request and contract

Keep one coordinator responsible for the finished result. Retain the exact original request and applicable constraints before producing a candidate. The native runner requires contract `schema_version: 2` at creation and every resumed transition. The standalone [requirement checker](../harness/requirements_check.md) accepts v1 for diagnosis and migration; create a v2 contract for a native run.

Register every required artifact, action, content condition, prohibition and evidence condition. Bind each requirement to an exact request quotation and its target. For content, prohibition and evidence conditions, use `message://final` for the complete final response and `artifact://path` for a file in the artifact snapshot. Retain artifact requirements as `path` records and action requirements as exact operation/target pairs. Record a `source_span` when the request quotation needs an exact occurrence; its Unicode-character range must match `source_text`. Give each content, prohibition and evidence condition a supported evaluator, evidence references and initial `pending` status. Derive results from the checker and actual returned evidence. Keep each requirement's owner, target version, result and current status in the operational map. Record omitted outputs as unmet requirements.

Before candidate production, independently extract obligations from the fixed original request without showing the candidate, then compare the extraction and proposed contract in both directions. Draft-only author coverage remains labeled self-check and cannot approve release. Retain output, content, prohibition, action, authority and completion classifications, exact source spans/quotes/hashes, reasons for non-obligations and unresolved ambiguity. Supply the original request, contract and policy bindings. Keep the candidate out of this review. The original publication coverage return uses schema 3 with the independent bidirectional extraction; schema 2 is draft diagnosis only. It includes `coverage_rows` that partition the full request into exact source spans and link each obligation to its requirement IDs. Derive these rows from the request before seeing a candidate; distinguish a required literal from a claim about what that literal measures. The reviewer returns the request-span map in its original structured `requirements-coverage` report. Resolve omissions, mismatches and unassessed conditions, then import the passing return with `begin --run-dir RUN --coverage-review coverage.json`. Strict submission requires that return. Assign this review to the selected coverage worker before its candidate audit when reusing that actual worker. Record assignment purpose, previously seen inputs and when the original request was provided. That worker performs request–candidate consistency, with distinct coverage and candidate returns; it cannot also represent a request-unread comprehension observation.

Select a registered `--operation` at `begin`, supply its activated `--condition` values and select a registered `--profile` and any `--template` resources. Use registry IDs for profiles and templates. At `begin`, pin the request, contract, mode, adoption selection, the `policy_id` returned by the selected manifest and its exact target bytes. The [policy manifest](../quality/policy_manifest.json) binds the adopted instruction and checker dependency closure. Include the prose dictionary and guide, runtime rules, selected skill and operation, selected writing profile, consumed templates, registries and referenced dependencies. Recheck these bytes at every transition. A changed adopted dependency invalidates the run's policy binding; create a new recorded run with the revised adoption and repeat affected checks. Reading selection is separate: `select_reading_sections` returns registered resource/section IDs for the current stage, role and unmet conditions within this fixed closure. Record actual read ranges by reader ID, resource hash and section ID; retain partial unread ranges for the next read. A stage or reader change preserves the manifest hash and run ID. Same-version recorded ranges can be reused; the cache does not prove model consumption.

For inherited requests or adopted specifications, register their exact text, source IDs, versions and hashes in the v2 contract sources. Bind every requirement to its source_id and source span; partition every registered source in the existing coverage return. Use forbidden_operation with the actual operation and target for an operation prohibition; forbidden_literal tests output text. Keep original requests and prior contracts intact. Link every authorized requirement change to the user's actual instruction and its source. Compare the change with the conversation before adopting it. Preserve required outputs and conditions until the user changes them. Record proposed work, authorization, attempted execution and returned outcomes as separate states. Keep review findings, repairs and attributable results in operational records; exclude private reasoning and credentials.

## Worker roles and identities

As the first control operation, request and, when the host supports it, actually start or resume one instruction-compliance/reminder worker. Record requested, observed-running, receiving-evidence and completed, or unavailable/failed, from actual host results. Reuse the same assignment and actual ID through resumption. Supply the [TEAM assignment](TEAM.md#shared-work), fixed request/policy references, current short packet, actual parent/child IDs and candidate/unmet state. Ask it to preserve instructions, require the next check, return deviations for repair and reconfirm the final candidate before termination. A missing start stays unavailable; a later available host capability may fulfill the same request. An MCP/UI response or an accepted send queue is not a worker start, received message or completed check.

For completed-output review, assign distinct actual quality A and quality B, both different from the author, and the compliance role. Preserve request-only coverage before candidate production; quality assignments receive the fixed request, contract, policy, full candidate and determining sources. Do not share developing A/B judgments before both original returns are fixed. Bind actual start/end and original returns to the same run, request, policy, candidate and artifact set. A worker name, copied return, claimed pass, made-up event, stale candidate or missing terminal return cannot satisfy independence. The reminder role maintains control instructions and never substitutes for independent prose quality.

Use actual host start/resume/message operations; do not add fictional plugin permissions. Follow TEAM for unavailable or relay-only communication. Trusted Work/Codex hooks are a separate event-driven path. Keep source verification and record consistency distinct from host-authenticated release authorization. Necessary unavailable capacity remains unmet while useful labeled draft work proceeds.

## Role-specific work

Read the instructions and sources governing the assigned result:

For explicitly requested artifact-only comprehension, assign a context with no prior request/candidate/authoring-history exposure and record that exposure state. Provide the candidate and permitted substantive references, fix its reconstruction, then supply the original request for comparison. A reviewer already used for request coverage audits request–candidate consistency instead. Record these as different observations, never relabel prior exposure as a fresh context. Use the existing number of assignments required by the task; report an unavailable fresh context as unperformed.

- Execution: CORE, the selected specialist and applicable PROSE/EXECUTION sections. Produce the requested artifact or action outcome.
- 2A: the [checker guide](../quality/prose_rules.md), A/B/C definitions in the [JA/EN dictionary](../quality/prose_rules.json), fixed request and contract, candidate and determining source inputs. Mechanically scan every rule; reviewers read matching rules and related technical-term definitions rather than rereading the entire dictionary. Retain commands and results, inspect meaning and rhetorical function throughout the candidate, and dispose of every scanner match. Each correction identifies location, rhetorical or paragraph function, proposed rewrite, target proposition and source reference.
- 2B: the original request, fixed contract, original inputs and applicable domain/meaning rules. Perform the pre-candidate coverage review, then independently audit the complete candidate for requested content, requested derivations, structure, format and rhetoric. Read the checker's A/B/C criteria. After fixing independent findings, rerun the affected checks and bind execution status to its returned event. Verify exact source quotations and bibliography spans against the independently pinned source inputs. Apply [Full-candidate prose records](CONTROL.md#full-candidate-prose-records) for occurrence resolution, fixed definition evidence, whole-candidate judgments and the checker’s structural scope.
- 3: the brief, requirement map, observable operations and returns, revisions, fixed reviews and final candidate identity. Check scope, authority, requested work, refusal grounds, completion claims, required checks and post-review changes. Use observable conduct and returned evidence.

Record every mechanical run's inspected version and returned outcome. Label manual inspection as manual. Run the task's requirement, candidate and prose checks against its current inputs.

## Full-candidate prose records

Keep begin request, authority, policy and original sources fixed. Add newly acquired or computed evidence through submit --evidence DIR, with the run-bound manifest, content hashes, actual call/return and premise bindings specified in [native check](../harness/native_check.md). Snapshot this evidence with the candidate and artifacts; update affected quality returns whenever its sources_sha256 changes. Generated explanations, circular references and different-input calculations cannot serve as admitted evidence. Acquired source evidence uses the registered document and web acquisition adapters in native check. Existing quality reviewers establish document identity, actual body access and claim support; the checker binds the exact call target and returned passage. Bind the evidence manifest to the current canonical run_id even in direct checks; numeric result spans cannot split a different quantity.

Each selected quality role generates original quality schema version 3; the reader retains schema version 2 compatibility. Register `claim_evidence` for the propositions under examination, once with exact target path/hash/raw span/quote, claim kind and typed source correspondence in `evidence_sources`. Nonpropositional headings, connectors and list markers are structure assessed in whole-text meaning and organization review. A heading containing a conclusion or number belongs in the proposition ledger. The reviewer compares the complete candidate and text artifacts with the ledger to identify omitted claims; a mechanical numeric guard is not semantic coverage proof.

Distinguish request-adherence, user-supplied-value, source-observation, assumption, derived-result and operation-complete. Request-instruction supports task conformity; supplied-value and supplied-assumption point to the corresponding original request span. Observation requires original-source propositions or stored calculation results. Numeric derivation requires adopted premises, the actual executed command and its validated calculation result; logical derivation and choice comparison require premises and a concrete inference or comparison. Operation completion requires its validated operation return. Generated artifacts cannot serve as admitted sources. The reviewer extracts and classifies each claim from the candidate and records its source correspondence.

Each quality role returns a common `candidate_sha256`, `claim_ledger_sha256`, `review_scope` containing every final text path and a concrete whole-text `assessment`. The ledger hash is the canonical hash of claim_evidence and evidence_sources. Return all 22 existing B25–B31/C01–C15 IDs in `prose_verdicts` as absent, violation or unassessed; consistency requires absent for all. Concrete findings and unassessed records retain check ID, exact target hash/span/quote, assessment and affected claim references. Do not repeat all K claim IDs under every one of 22 judgments. Each selected worker still performs its own whole-candidate review, including supplementary/annotative framing and conduct. Confirm text views against rendered artifacts when applicable.

Machine scanning applies all 142 dictionary rules and retains all raw/display positions and duplicate matches. Every match enters `occurrence_judgments`: function, meaning, syntactic role, target proposition and exact source correspondence when required. This generalizes existing technical/different-word/source records; the reader converts those old formats. Register a non-rhetorical occurrence only after establishing its exact use and whole-proposition function. A code, quotation or specialist label cannot clear a function; quotation selection and generated explanation are also assessed for prohibited functions. Source quotation/bibliography requires the pinned original source range and exact bytes. Change a quotation only as a labeled paraphrase, never retain an altered string as original quotation. See [native check](../harness/native_check.md) for the generated schema and legacy conversion.

## Original returns and correction

The quality roles and any monitor selected by the registered plan return original structured JSON against the exact candidate before integration. The canonical object contains `schema_version`, `role`, `decision`, `findings`, `unassessed`, `errors`, `checks` and candidate/input bindings, plus the shared candidate/claim ledger bindings, 22 verdicts, occurrence judgments and verification fields used by its decision. Preserve the exact `return_text` bytes and hash. Derive the normalized result from that original. Every envelope copy must match the original. Obtain a new original return to repair failed, incomplete, conflicting or unstructured review records.

Resolve material disagreement at the source, rule or calculation. Keep unresolved findings in the record and prevent a full pass. Repeat a review after its assessed inputs or identified error changes. Keep one active assignment for each role and candidate. Compare the existing candidate hash and unresolved finding IDs before repeating a failed submission. Repair the determining cause or obtain the exact missing input or evidence; do not repeat an unchanged failed combination. Fresh evidence can support a new assessment of unchanged candidate bytes.

Delete the author's prohibited rhetorical functions without exceptions. Remove supplementary and annotative wrappers; relocating the wrapper into a footnote, postscript, caption or status message does not resolve it. Resolve every dictionary match by its occurrence function, meaning/syntax and exact source identity. Rewrite prohibited functions into direct propositions or delete them; recheck the surrounding text and finished result. Finite word lists, spelling and quotation/technical labels alone never clear a match. Rescan every revision and obtain the independent review required by the pinned plan against original inputs.

After a revision, the quality roles selected by the registered plan inspect the new final candidate and affected dependencies and return updated candidate-bound decisions under that plan’s self-check or independence requirements. Reuse calculations and source inspections whose inputs still match. Bind final-text approval to the current bytes. Record each finding's repair or unresolved condition and respect the user's resource limits.

## Finalization and delivery

Fix the exact outgoing bytes for each surface: final, progress, status or error. Apply the complete 142-rule scan and both existing quality roles' 22 whole-text meaning judgments to that same surface/hash, using its fixed source and actual operation evidence. `scan-text --require-clean --surface SURFACE` reports lexical-clean for zero hits and never grants sending permission; scan completion, lexical matches, semantic review and release authorization remain distinct. Submit the same text through the existing native run with `surface=...`; keep the original request, parent contract and current task state. On the Site, use the returned `surface_id` for its direct role submissions and surface-only release as specified in [Site outgoing-surface routing](../harness/native_run.md#site-outgoing-surface-routing); preserve the parent final candidate and its review records. The returned surface_check binds surface, text_sha256, evidence_event_ids, scan_complete, lexical_hits, quality_a_prose_verdicts, quality_b_prose_verdicts and unresolved. An unfinished parent artifact, action or final-content requirement remains in parent_unmet and cannot authorize final delivery; it alone does not invalidate a fully reviewed progress surface. Preserved prohibitions, invalid inputs and unmatched execution evidence still block that surface. Select progress content from returned operation records, remaining requirements and the next resolving operation. A generated status sentence also undergoes the same whole-text review. Resolve lexical hits by repair or candidate-bound occurrence judgments; a zero-hit scan and unreviewed JSON cannot replace meaning judgments. Record exact hashes and actual returns in the existing run. The native checker reports review consistency and keeps release_authorized false; the execution owner must connect any actual send/save to the adopted host verification and publication predicates. Ordinary Chat transmission has no automatic interceptor in this plugin. Final delivery still requires the complete parent contract and native finalization on identical bytes. Hooks and MCP/UI retain the same short command and unmet IDs after every tool; UI acceptance proves neither consumption nor adherence. Interrupt/cancel/stop/close/completion prevents reinjection from restarting the run. Child Stop checks its assigned return and required checks, not parent finalization. Inspect requested attachments, figures and actions; action claims bind the actual operation, target and returned outcome.

Await terminal outcomes for all required assignments. Pending, timed-out, cancelled, failed and missing outcomes remain unmet. The monitor's final return identifies outstanding findings and observation gaps and checks coverage of required actions. Obtain evidence for each missing event or keep its requirement unmet.

Confirm that every decision required by the selected plan binds this candidate, all material findings are resolved and each required action has its returned outcome. Submit the original returns with the unchanged candidate. Inspect computed failures, missing checks and unresolved findings. `finalize` rechecks the selected immutable submission and the common release predicates. It writes contract-requested artifacts and returns the exact final response only after strict-reviewed host authorization; verify-only uses the same predicates. Missing authorization preserves blocked-unapproved without final files or body. Deliver that snapshot and its exact response text. A subsequent edit, heading, caption or status sentence creates a new candidate and requires a new submission and affected checks. Preserve the mapping between the runner's byte manifest and the state helper's task/candidate hash.

Report the returned state: authorized published snapshot and performed checks, isolated provisional candidate and unmet checks, or blocked-unapproved run and exact prerequisite. Apply task permissions to external actions and stop at the requested completion condition.

## Commands and result meanings

Use the [native runner interface](../harness/native_run.md): `begin --run-dir RUN --request request.txt --requirements requirements.json --author-id ACTUAL_EXECUTOR_ID --operation REGISTERED_OPERATION --capabilities capabilities.json --sources original-sources`, import the coverage review, then `submit --run-dir RUN --candidate answer.md --artifacts candidate --events events.json` with current `--reports` and `--text-views`, followed by `finalize --run-dir RUN --submission-sha256 RETURNED_HASH --output NEW_DIR`. Supply capability and adoption inputs as specified by that interface. Read the computed status and `needed_actions` after each call. Obtain required returns through actual host tools, repair findings and resubmit.

Use [native_check.py check-native](../harness/native_check.md) for read-only record diagnostics. `consistent` identifies agreement among the inspected inputs and records. Native `full_pass`, `release_authorized` and `provenance.authenticated` remain `false`. Compare records with actual host events before describing performed work.

Use [local_checks.py](../harness/local_checks.md) `scan-text --input FILE --dictionary FILE` for targeted detection. Record the command, inspected version, returned scan state and matches. Resolve matches through the assigned quality review. Use native `finalize` to write the checked candidate and artifacts to a new local output directory.

Use shared display-character mappings for every occurrence. Technical definitions support occurrence review, not a finite whitelist. Bind unregistered definitions to the existing pinned original evidence. Professional context, necessity and quotation never exempt other matches. Preserve every overlapping rule ID while sharing one substantive judgment or repair for the same occurrence and function.

## Host-observed Site publication

An explicitly authorized host-observed deployment may use actual independent quality A, quality B and compliance workers, their direct authenticated-user submissions to the Site, and coordinator comparison with actual launches and original returns. The Site binds each receipt to its fixed run, review revision, candidate and policy hashes, role, server assignment ID, original-return hash, authenticated user and server receipt time. It retains the exact originals once. A candidate or adopted-policy change invalidates every affected receipt and match. Both quality judgments must be fixed before sharing; compliance then binds both originals. All 142 rules, all 22 full-candidate judgments, pre-candidate independent coverage, first compliance start and repeated reminders remain required.

The assurance class is host-observed: worker identities and coordinator observations are operationally checked by the host coordinator, not cryptographically authenticated by the Site. Hashes, submitted actor IDs and visitor authentication alone do not prove independence. No host-authenticated claim is allowed on this path. If a worker cannot directly access the submission tool, keep its submission unmet and report that limitation; the parent must not submit on its behalf while claiming direct delivery. Local runtime without a configured server observation remains blocked.
